# v0.4 增量迁移与恢复说明

本文是操作与验收依据，不表示正式升级、原文核对或真实模型验证已经完成。具体备份路径、执行时间、测试结果和服务状态应写入本次发布记录。

## 1. 迁移内容与兼容范围

应用启动由 `Repository.migrate()` 在 PostgreSQL advisory lock 和事务中依次执行缺失迁移。v0.4 当前接受 schema 1～5，最终 schema 版本为 5；schema 4/5 不应直接交给只支持 1～3 的旧应用启动。

`migration_004.sql` 做以下增量变更：

- 给 `experiences` 添加 `revision=1` 和原始来源 `source_hash`；为未删除原文计算 SHA-256，不改写 `user_text`、`assistant_text`、原有 ID、记录时间或已保存事件时间。
- 新建事件、精确证据、细节、线索、关联、版本、有效重提、向量和任务表；保存来源可靠性分类、编码版本、细节权重理由，以及日级/范围/未知时间精度；保留原有事实、消息、经历、自我状态及删除账本。
- 扩展 `context_links` 允许事件依赖；新增关联表不参与删除传播。
- 给模型调用记录添加阶段、来源 manifest、估算输入及策略版本；不迁移提示正文，因为系统不保存此类正文。
- 建立事件全文、时间和 HNSW 索引，登记 schema 版本 4。

`migration_005.sql` 在已初始化的 schema 4 上追加 `model_calls.estimator_version`，登记 schema 版本 5；旧调用记录保持为空，新调用记录实际使用的估算器版本。不要求清空已存在的 v4 实验数据。

SQL 迁移内不调用模型，也不做历史批量云端抽取。哈希计算发生在迁移事务内，历史量大时应预留本地扫描时间。复杂事件表示由后续 worker 分批建立，避免在 schema 事务中执行长时间模型任务。

事件投影的时间按原始时间引文重新保守解释；没有足够依据时可为 `unknown`。这不会改写 v3 原始经历中已有的时间字段，也不能把投影时间变化误判为原文迁移损坏。

## 2. 升级前准备与原文核对

在项目根目录执行备份，并记录命令实际返回的 `.hmem` 绝对路径：

```sh
python3 scripts/manage.py backup
```

备份密钥与最新独立删除账本必须一并保全，且分别保管；不要把它们复制进仓库、报告或聊天。此次升级的具体备份路径由发布记录提供，本文件不写入假设的文件名。

若需要回退到旧应用，升级前还必须保留可运行的 v0.3 镜像及对应代码/Compose 配置。此项目没有 Git 历史可作为自动恢复依据；仅保存数据库备份不足以恢复旧应用版本。

在不输出个人正文的情况下，为原始经历做前后核对：

1. 记录未删除经历数量、ID 集合和关键时间字段摘要。
2. 按相同规则计算每条原文哈希：`SHA256(UTF8(user_text + U+001F + assistant_text))`；将 ID 与哈希对应关系保存在受保护的本地验收资料中。
3. 升级后比较原文哈希、ID 和时间字段；新列 `revision` 应为 1。发生合法的新写入或删除时，应先停写或明确时间边界，避免将并发业务变化误判成迁移损坏。
4. 已删除记录按删除账本处理，不为了核对而重新读取或恢复其正文。不能只以新事件数量判断原始经历是否完整，因为一轮可能分成多个事件。

验证数据使用合成内容。涉及正式库的核对报告仅记录计数、布尔检查结果与必要的技术哈希，不导出聊天正文。

## 3. 切换、回填与运行观察

代码复制进镜像，单纯重启旧容器不会加载新代码。验证通过后才进行正式构建和切换：

```sh
docker compose build api
docker compose up -d --force-recreate --wait api worker
python3 scripts/manage.py status
docker compose logs --tail=100 api worker
```

API 与 worker 启动都先迁移，再重放独立删除账本；迁移失败不会完成 schema 事务。应用 schema 不支持、删除账本缺失/损坏等情况应修复后再开放服务，不通过删除账本或重建空目录绕过启动检查。

旧经历的事件回填由 worker 每轮维护最多处理 100 条，约每 60 秒执行一次。回填只使用现存原文和现有本地描述；不推断已经丢失的历史，不自动把旧对话发送给云模型。它按是否已有事件证据判断完成状态，可以中断后续跑。

在旧经历尚未回填时，查询提供只读兼容事件：

- `legacy_projection=true`，临时事件 ID 使用原始 `experience_id`，来源仍是原始经历。
- 兼容表示参加同一活跃度与预算流程，不因预览而写入新事件。
- 它不能作为真实事件 `target_id` 接受补充，也不能冒充已经存在的事件供自我解释引用；原始经历来源仍可引用。
- 回填后会产生真实事件 ID，因此客户端不要把 legacy ID 当作永久事件 ID。原始经历 ID 保持不变。

向量重建独立于原文和全文索引。索引尚未完成或嵌入不可用时，关键词、线索、时间及可用关联仍可工作。观察 `/health` 的版本、事件计数、各索引队列状态，并检查失败任务；这些状态说明运行进度，不等同于记忆效果验证。

## 4. 删除、备份恢复与回退

删除意图先写入独立账本并 fsync，再进行数据库擦除。数据库事务失败时，该意图仍会在下次启动或恢复时保守重放。删除账本只记录标识与时间，不保存被忘记的内容；v0.4 没有新增“只删事件投影但保留原文”的公开遗忘语义。

备份使用流式加密封装：每份备份派生独立密钥，按顺序认证数据块，并用认证结束帧检测截断。恢复继续兼容旧封装。以下命令的路径必须替换成实际存在且经过记录的备份文件：

```sh
python3 scripts/manage.py restore /绝对路径/实际备份.hmem
```

恢复流程先将解密结果送入独立暂存数据库，确认完整认证成功后迁移并重放最新删除账本。随后停写，保存当前库的加密回退副本，再次重放账本，然后原子切换数据库名称。新服务健康后才删除旧库；切换后失败会尝试换回原库。明文 dump 经进程管道传输，不落地为普通文件。

恢复旧备份不允许恢复后来明确删除的内容：最新账本会继续擦除旧快照中的原文、事件摘要、细节、线索、向量和衍生自我状态。缺失、截断或比备份所要求的历史更旧的账本会使恢复失败。保护好最新账本，不能随数据库一起回滚。

需要区分两类回退：

- **数据恢复，继续运行 v0.4：** 直接使用当前恢复工具。即使输入是 v0.3 备份，当前工具也会将暂存库迁移到当前 schema 5 后再开放，不会把应用降级。
- **应用回退到 v0.3：** 没有自动降级 SQL。需停写并备份当前 v4 状态，选择保留的 v0.3 镜像/代码/Compose 配置，使用其兼容恢复流程恢复升级前备份，同时保留并重放最新删除账本。升级后新写入不会自动回到升级前快照；应在回退决策中明确这段数据的处理。不要通过手工删表或删除 schema 版本号强行降级。

对于已产生较多 v4 新数据的安装，优先修复兼容当前 schema 的应用；盲目恢复旧快照会丢失升级后的有效写入。

## 5. 验收项目与结果记录

测试和验证依次运行，不并行操作隔离验证环境：

```sh
python3 scripts/manage.py test
python3 scripts/verify_memory_v4.py
python3 scripts/verify_memory_v4.py --real-model
python3 scripts/verify.py
```

`verify_memory_v4.py` 默认检查真实本地 BGE 检索等阶段；只有加 `--real-model` 才检查实时模型生成。性能报告会区分完整向量索引和仅全文索引，不能把不同模式的数据混为一组。需要全部性能数据完成向量索引时使用 `--full-index`，并按实际耗时与资源安排。具体通过项、失败项、跳过项应来自脚本生成的报告，本文件不预先承诺通过率或延迟。

存储与迁移至少检查：

- 原文前后哈希、ID、时间不变；旧事实/经历接口可用；重复启动不重复迁移。
- 多事件、跨轮补充、重复短语位置、发生时间与记录时间正确，故事不会变成现实亲历。
- 回填中断可以续跑；未完成回填时的查询不写入数据库；私有和陈旧来源不进入云端上下文。
- 旧任务晚完成、回答途中删除、事件版本变化及隐私撤回不能复活内容；事务错误不留下部分新原文或新自我状态。
- 逻辑时钟推进会改变活跃度、事实有效期与当前情绪，但不改变 worker 租约或原文；预览不计有效重提。
- 从旧备份恢复后，最新删除账本仍擦除新旧派生表示；错误密钥、篡改、截断及不完整账本不会替换正常在线库。
- 实验台使用独立数据、账本、逻辑时钟及合成内容；它的结果与正式记忆分开，mock/fake 模式不标成真实模型/真实向量结果。

发布记录应列出实际备份路径、旧镜像/配置保留位置、核对结果、执行过的测试命令及报告路径、部署时间和健康状态。尚未执行的项目明确标记待验证。
